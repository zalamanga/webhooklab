# WebhookLab design read

The user's retained direction is a light, orderly work application, with real screenshots and explanatory documentation. The accepted project is a webhook delivery laboratory. The choices below interpret that direction; they are not additional user quotations.

ENERGY 1 / RHYTHM 2 / MOTION 1. The audience is a developer inspecting an event, its delivery attempts and the receiving system's evidence.

- Use a light neutral work surface, dark readable ink and one restrained cobalt action accent. Amber/red are semantic retry/error signals, always paired with text.
- The identity motif is the delivery attempt sequence: event, numbered attempts, receiver receipt. This sequence is real stored data, not decorative network art.
- Give the event payload and attempt timeline different structures: a readable JSON block and a chronological evidence list. The delivery register is genuinely tabular, with a local scroll region on small screens.
- Use system sans-serif for reading; monospace only for JSON, event IDs, HTTP status and signing-header names. No external font service is required.
- Top-level navigation follows the work: Deliveries, Send event, Demo receivers and Audit. The application name is text; no new graphic logo, avatar or stock illustration is needed.
- Clear rectangular buttons and modest sheet radii identify controls and working areas. Flat surfaces avoid decorative shadows, glass and glow.
- Desktop uses a compact work navigation bar and wide evidence area. Mobile stacks event/attempt/receipt sections and keeps actionable controls at least 44 px tall.
- Distinguish waiting for delivery from request loading, and distinguish delivery failure from an unknown remote outcome. Show polling/update time instead of implying an uninterrupted live stream.
- Show all demo endpoints and payloads as synthetic/local. No invented customer counts, delivery statistics, service uptime or security certification.
- Motion is limited to focus/hover feedback. No autoplay, animated counters or entrance choreography.

The primary agent will run the final UI gate against the built application and record actual evidence in UX-REVIEW.md.
